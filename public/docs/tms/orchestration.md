# Workload Execution and Monitoring

- TMS treats every workload — job, API, or pipeline — as a Kubernetes object.  
- Each workload runs in its own namespace under the user’s cluster.  
- All deployments are created via YAML generated by the backend and committed to Git.  
- ArgoCD applies those manifests automatically.
- Jobs: one-time or scheduled cron jobs.  
- APIs: long-running services or containerized endpoints.  
- Pipelines: multi-step GitHub workflows running inside EKS using runners.  
- Dashboards: Grafana-based analytics or monitoring views.  
- Each type uses the same deployment engine but different templates.
- When a user deploys a workload:  
    - The backend generates a manifest (Deployment, CronJob, or Job).  
    - It commits it to the GitOps repo under `/workloads/<type>/`.  
    - ArgoCD syncs the change and spins up pods in the user’s namespace.  
    - TMS watches pod events, logs, and resource usage using the Kubernetes API.  
- No direct cluster access is required — everything runs declaratively.
- All pods send logs to Loki via Fluentd.  
- Users can view logs from the TMS UI in real time.  
- Logs are indexed by job ID, namespace, and pod name.  
- Old logs are archived automatically based on retention rules.
- Prometheus collects metrics from all namespaces.  
- Grafana dashboards show:  
    - CPU and memory per workload  
    - Success/failure ratio for jobs  
    - API latency and uptime  
    - Container restart counts  
- Each metric links back to its workload in TMS.
- Each job and API includes cost annotations.  
- Prometheus metrics are aggregated with AWS CUR data.  
- Users can view cost by:  
    - Cluster  
    - Namespace  
    - Workload  
    - Time range  
- This helps identify expensive pipelines or inefficient deployments.
- TMS uses Kubernetes Horizontal Pod Autoscaler (HPA).  
- APIs scale based on CPU or request load.  
- Jobs and pipelines scale based on queue depth or cron concurrency.  
- All scaling thresholds are configurable in the UI or YAML.
